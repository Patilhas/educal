\chapter{Conclusion} \label{cap:conclusion}

At the conclusion of the project timeline, EduCal has moved from a conceptual set of requirements to a functional web application that replaces the spreadsheet-based process previously used for institutional academic planning at ISEL (Chapter~\ref{cap:background}). Of the six functional requirements defined in Section~\ref{sec:functional-requirements}, four were fully implemented and are in use: hierarchical event and occurrence management (RF01, Sections~\ref{sec:core-entities} and~\ref{sec:frontend-event-dialogs}), the idempotent, rule-aware academic-year Migration Engine (RF02, Section~\ref{sec:migration-engine}), the configurable Business Rule Engine (RF03, Section~\ref{sec:rule-engine}), and role-based multi-user access control (RF06, Sections~\ref{sec:backend-authentication}, \ref{sec:backend-rbac}, and~\ref{sec:frontend-user-mgmt}). Notification support (RF04) was partially delivered: the in-app notification bell (Sections~\ref{sec:backend-notifications} and~\ref{sec:frontend-notifications}), reminding users of upcoming occurrences within a configurable lead time, is implemented and in use, but the requirement's other half, a manually-sent email template field, was not, and neither was Excel schedule export (RF05); both are discussed as concrete next steps in Chapter~\ref{cap:future-work}.

The decision to structure the backend as a decoupled Controller-Service-Data pipeline, with all storage access hidden behind a repository interface (Section~\ref{sec:data-access}), proved effective throughout the project. It allows the migration engine, the rule engine, and the notification system alike to be developed and iterated on independently of the underlying data store, and it makes the transition from the JSON-backed mock data used while developing the business logic to the production PostgreSQL database a matter of changing a single environment variable, with no changes required to the controllers, services, API routes, or frontend. The same separation is what makes it possible to keep the lightweight Redis-backed implementation alongside PostgreSQL for development and demos, without either implementation leaking into the rest of the system; the notification feature's own Redis repository reuses this shared base class directly, rather than introducing a new one.

Overall, EduCal addresses the core problem stated in Chapter~\ref{cap:background}, the manual, error-prone, spreadsheet-based rebuilding of the academic calendar every year, through automated migration and configurable rule checking, backed by a secure, role-based multi-user system and proactive in-app reminders. The remaining gaps, the email template field, schedule export, and the ISEL VM deployment, are detailed in Chapter~\ref{cap:future-work}.
