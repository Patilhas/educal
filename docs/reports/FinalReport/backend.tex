\chapter{Backend} \label{cap:backend}

This chapter details the backend implementation of EduCal, covering its layered organization, authentication, authorization, error handling, and testing approach.

\section{Organization} \label{sec:backend-organization}

The backend is organized per feature (\texttt{auth}, \texttt{calendar}) under \texttt{server/}, each following the same three-layer structure of Controller, Service, and Data, plus a \texttt{server/shared/} module for cross-cutting concerns (the API response envelope, domain error type, and the data-layer factory). This mirrors the Controller-Service-Repository pattern used since the initial implementation: controllers such as \texttt{authController} and \texttt{calendarController} act as orchestrators that parse and validate the incoming HTTP request and hand off to the corresponding service, keeping the route handlers in \texttt{app/api/**/route.ts} as thin, near-identical wrappers regardless of feature or HTTP verb, for example \texttt{export const POST = withApiAuth((req) => calendarController.createEvent(req))}. Neither the route nor the controller action parses the request itself, checks the role, or catches errors directly: \texttt{withApiAuth} (Section~\ref{sec:backend-authentication}) resolves the session cookie into a user before the handler runs, and every failure, whether it comes from validation, authorization, or the database, is funnelled through the controller's own \texttt{fail()} call (Section~\ref{sec:backend-error-handling}).

\section{Authentication} \label{sec:backend-authentication}

Passwords are never stored in plain text: they are hashed with Node.js's built-in \texttt{crypto} module~\cite{nodejscrypto} using \texttt{scrypt}, a per-password random 16-byte salt, and a 64-byte derived key, encoded as \texttt{scrypt\$salt\$hash} and stored in \texttt{users.password\_hash}. Verification re-derives the hash from the candidate password and the stored salt, then compares it against the stored hash with a constant-time comparison (\texttt{crypto.timingSafeEqual}) to reduce the risk of timing attacks; the two hashes' lengths are compared first, since that call throws on mismatched buffer sizes. The full implementation of both functions is given in Appendix~\ref{app:crypto} (Listing~\ref{lst:crypto-full}).

On login, the service generates a random 48-byte, base64url-encoded session token and persists it, with its expiration, in the \texttt{sessions} table: a short-lived session (1 day) by default, or 30 days when the user selects ``Remember Me'' (\texttt{staySignedIn}). The token is sent as a cookie that is \texttt{HttpOnly}, \texttt{Secure} in production, and \texttt{SameSite=Lax}~\cite{owasp}, carrying a \texttt{maxAge} only when ``Remember Me'' is selected. Every authenticated request also re-validates the session server-side against its stored expiration, deleting it if expired.

\section{Error Handling} \label{sec:backend-error-handling}

API responses follow a consistent envelope: \texttt{\{ data: ... \}} on success, \texttt{\{ error: \{ code, message, details \} \}} on failure. Domain-level failures are raised as a typed \texttt{DomainError} (an error code such as \texttt{UNAUTHORIZED}, \texttt{FORBIDDEN}, \texttt{NOT\_FOUND}, or \texttt{CONFLICT}, plus an HTTP status), and Zod validation failures become a \texttt{VALIDATION\_ERROR} with a structured, field-level breakdown. Every controller method funnels its errors through this single \texttt{fail()} helper, so the frontend always receives a predictable error shape regardless of which layer raised it.

\section{Role-Based Access Control} \label{sec:backend-rbac}

Three roles are supported, \texttt{viewer}, \texttt{editor}, and \texttt{admin}, ordered in a strict hierarchy. Calendar-editing operations (creating, updating, or deleting events, occurrences, and vacation periods, and running the migration engine) require at least the \texttt{editor} role; user management requires the \texttt{admin} role. Authentication itself is enforced by HTTP-level middleware (\texttt{withApiAuth}/\texttt{withApiAuthContext}) that resolves the session cookie into a user and rejects unauthenticated requests before they reach a controller; role checks are then applied one layer down, inside the services.

Rather than scattering an \texttt{if (role !== "editor") throw ...} check across each service method, role enforcement is centralized in a single generic wrapper, \texttt{withRolePolicy}, applied once per service. It takes the service instance, a policy map from method name to a minimum role (or \texttt{"any"}), and a \texttt{getRole} function reading the caller's role off that method's own arguments (Section~\ref{sec:backend-controller}), and returns a new object where every listed method asserts the minimum role before delegating to the original. The design is deny-by-default at the type level, not only at runtime: a method the policy map omits is absent from the returned object's type entirely, so adding a service method without a matching policy entry fails to compile at every call site. \texttt{calendarService} and \texttt{authService} are both exported this way, e.g. \texttt{listEvents: "any"} alongside \texttt{createEvent: "editor"}; the full implementation is in Appendix~\ref{app:with-role-policy} (Listing~\ref{lst:with-role-policy-full}).

Beyond the basic role hierarchy, the system enforces three self-management invariants to prevent an institution from locking itself out of administration:
\begin{itemize}
    \item an administrator cannot demote their own account away from \texttt{admin};
    \item an administrator cannot delete their own account;
    \item the last remaining administrator cannot be demoted or deleted; the service counts existing admins before allowing either operation and rejects it if only one would remain.
\end{itemize}

\subsection{Controller} \label{sec:backend-controller}
Controllers (\texttt{server/auth/controllers/}, \texttt{server/calendar/controllers/}, \texttt{server/notifications/controllers/}) are the entry point for each API route. They parse and validate route parameters and the request body, invoke the corresponding service method, and translate the result, or any error thrown, into an HTTP response using the shared \texttt{ok()}/\texttt{fail()} helpers. This is also where the session cookie is set on login and cleared on logout. Listing~\ref{lst:notification-controller} shows the notification controller's \texttt{markRead} action, a minimal case of this shape.

\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[caption={[Controller layer example.]{Controller layer example (\texttt{server/notifications/controllers/notification.controller.ts}).}}, label={lst:notification-controller}]
async markRead(request: IRequestWithAuth, notificationIdValue: string) {
  try {
    const notificationId = parseNotificationId(notificationIdValue);
    await notificationService.markRead(request, notificationId);
    return ok({ read: true });
  } catch (error) {
    return fail(error);
  }
},
\end{lstlisting}
\end{minipage}

The method does no business logic of its own: it validates that a notification id was actually supplied, delegates the read entirely to \texttt{notificationService.markRead}, and converts either outcome into the standard response envelope (Section~\ref{sec:backend-error-handling}). The \texttt{try}/\texttt{catch} boilerplate is identical across every controller action in the codebase, which is precisely what keeps the layer thin: nothing here depends on how a notification is read or where it is stored.

\subsection{Service} \label{sec:backend-service}
Services (\texttt{server/auth/services/auth.service.ts}, \texttt{server/calendar/services/calendar.service.ts}, \texttt{server/notifications/services/notification.service.ts}) hold all business logic and authorization checks, and are the bridge between the controllers and the data layer. This is where the RBAC invariants described in Section~\ref{sec:backend-rbac} are enforced, and where the central pieces of calendar business logic live: the Migration Engine (Section~\ref{sec:migration-engine}), the Business Rule Engine (Section~\ref{sec:rule-engine}), and the notification lead-time computation (Section~\ref{sec:backend-notifications}), which decides whether a notification is due for a given occurrence by comparing its effective lead time, in working days, against the current date each time notifications are read, rather than on a schedule.

\subsection{Data} \label{sec:backend-data}
The data layer (\texttt{server/auth/data/}, \texttt{server/calendar/data/}, \texttt{server/notifications/data/}) exposes a repository interface per feature (\texttt{IAuthRepository}, \texttt{ICalendarRepository}, \texttt{INotificationRepository}), abstracting all storage access; \texttt{INotificationRepository}, for instance, is six methods, \texttt{listAll}, \texttt{insertMany}, \texttt{deleteManyByOccurrenceIds}, \texttt{listReadNotificationIdsForUser}, \texttt{markRead}, and \texttt{markAllRead}, with no mention of SQL or Redis anywhere in it. Services depend only on this interface, never on a concrete database client, which is what enables the pluggable PostgreSQL/Redis backend described in Section~\ref{sec:data-access}: \texttt{NotificationRepositoryPostgres} implements it directly against the \texttt{notifications}/\texttt{notification\_reads} tables (Section~\ref{sec:data-model}) with Drizzle queries, and \texttt{NotificationRepositoryRedis} implements the same interface against a single JSON blob in Upstash Redis.

\section{Migration Engine} \label{sec:migration-engine}

The migration of the academic calendar from one year to the next is implemented as a single service operation (\texttt{CalendarService.migrateAcademicYear}), exposed to editors and administrators through dedicated ``Validate'' and ``Migrate'' actions in the calendar header (Section~\ref{sec:frontend-academic-year-tools}).

\begin{itemize}
    \item \textbf{Vacation periods first:} for the target academic year (source year $+\ 1$), the engine migrates vacation periods before events, so subsequent rule checks against the target year already see the correct vacation windows.
    \item \textbf{Idempotent event migration:} every source-year event is fingerprinted from a fixed subset of its fields (excluding database-generated ids); an existing equivalent in the target year is skipped, otherwise the event is cloned, so the operation is safe to run more than once.
    \item \textbf{Date shifting and leap years:} each occurrence's dates shift forward one calendar year; the 29th of February is clamped back to the 28th when the target year is not a leap year.
    \item \textbf{Validation, not automatic correction:} immediately after migrating, the full business rule set (Section~\ref{sec:rule-engine}) runs against the result, and any violations are collected into a report rather than auto-corrected, left as a manual step guided by the issue report shown in the application (Section~\ref{sec:frontend-academic-year-tools}). The same logic powers the standalone, read-only ``Validate'' action.
\end{itemize}

Listing~\ref{lst:shift-date} shows \texttt{shiftDateByYears}, the pure function every occurrence's start and end dates are passed through during migration, which implements the leap-year clamping described above.

\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[caption={[Date shifting with leap-year clamping.]{Date shifting with leap-year clamping (\texttt{shared/calendar/academic-year.ts}).}}, label={lst:shift-date}]
export const shiftDateByYears = (dateValue: string, years: number): string => {
  const source = new Date(dateValue);
  const target = new Date(dateValue);
  target.setUTCFullYear(source.getUTCFullYear() + years);

  if (target.getUTCMonth() !== source.getUTCMonth()) {
    target.setUTCDate(0);
  }

  return target.toISOString();
};
\end{lstlisting}
\end{minipage}

Adding one year to a date is not simply incrementing its year component: calling \texttt{setUTCFullYear} on the 29th of February of a leap year silently rolls the date forward into the 1st of March whenever the target year is not itself a leap year, since the 29th of February does not exist there. The function detects this by checking whether the resulting month still matches the source month; if it does not, the date is rolled back with \texttt{setUTCDate(0)}, which JavaScript resolves to the last day of the previous month, that is, the 28th of February. Every other date is left unaffected, since shifting a day that exists in every year by whole years never changes its month.

\section{Business Rule Engine} \label{sec:rule-engine}

A modular rule engine validates event occurrences against configurable institutional constraints. Each rule is a self-contained unit implementing a shared interface; the engine itself has no knowledge of what a rule checks, it only calls the rule's \texttt{validate} function and collects the result. Rules are registered in a single, central list the engine iterates over, so a new institutional rule is added by writing one file and registering it, with no branching logic and no changes to the migration or validation code. This same registry also drives the rule-configuration UI in the event form (Section~\ref{sec:frontend-event-dialogs}), which reads each rule's field metadata to render the matching controls.

\subsection{Rule Definitions} \label{sec:rule-definitions}

Every rule definition has the same four parts:

\begin{itemize}
    \item \texttt{id}: the stable key stored in \texttt{event\_rules.type} and used to dispatch validation.
    \item \texttt{fields}: the rule's configurable inputs and their defaults, read by the event form to render matching controls with no rule-specific UI code.
    \item \texttt{translations}: every user-facing string the rule needs, one display label plus one message per violation kind, keyed by locale.
    \item \texttt{validate}: a pure function taking the event, one occurrence, and the rule's configuration, returning zero or more violations, each carrying a message key and the field/date that triggered it, rather than a pre-formatted string, so the frontend renders every rule consistently (Section~\ref{sec:frontend-academic-year-tools}).
\end{itemize}

The Weekend rule (Appendix~\ref{app:weekend-rule}, Listing~\ref{lst:weekend-rule-full}) is a representative example: it flags an occurrence whose start date, end date, or any spanned date falls on a Saturday or Sunday. Weekend, Holiday, and Vacation period share the same three independent toggles, checkStart/checkEnd/checkRange, differing only in \emph{what} counts as a match on a given day; this shared loop is factored into one generic helper, \texttt{runDayRangeCheck} (\texttt{server/calendar/rules/utils/day-range-check.ts}), that each rule supplies with:

\begin{itemize}
    \item \texttt{matchDay}: a single-day predicate (``is this a weekend'', ``a holiday'', ``inside a vacation period''), tested against the start date, the end date, and, for \texttt{checkRange}, every day in between, stopping at the first match.
    \item \texttt{toViolation}: builds the rule's own \texttt{messageParams} from whatever \texttt{matchDay} matched.
\end{itemize}

An optional \texttt{matchRange} lets a rule replace that day-by-day walk with a single whole-interval check instead, which Vacation period uses since a vacation period is a continuous range rather than a set of independently meaningful days.

\subsection{Built-in Rules} \label{sec:built-in-rules}

Seven rules are currently implemented:

\begin{itemize}
    \item \textbf{Weekend:} flags occurrences whose start, end, or intermediate dates fall on a Saturday or Sunday.
    \item \textbf{Holiday:} flags occurrences that coincide with Portuguese national holidays.
    \item \textbf{Vacation period:} flags occurrences that overlap a registered school vacation period for that academic year.
    \item \textbf{Event no-overlap:} flags occurrences whose date span overlaps other, user-selected events.
    \item \textbf{Minimum gap to event:} enforces a minimum working-day gap between one event's end and a related, user-selected event's start.
    \item \textbf{Minimum duration:} always-on, enforces a minimum calendar-day duration, driven by the occurrence's own \texttt{minDays}.
    \item \textbf{Minimum gap to next occurrence:} always-on, enforces a minimum working-day gap between consecutive occurrences, driven by \texttt{minDaysToNext}.
\end{itemize}

The first five rules are selectively enabled per event through the event editor; the last two are always active and not exposed in the rule-configuration UI (marked \texttt{hidden} in the rule metadata). All rules are advisory: violations are surfaced for manual review, not enforced automatically, distinct from the structural, blocking validation Zod performs on every API request.

Most rules derive everything they need from the event and occurrence being validated, plus \texttt{context.allEvents}, for cross-event checks such as Event no-overlap. Vacation period is the exception: it consults \texttt{context.vacations} instead, a list populated from the per-academic-year Vacation Period table (Section~\ref{sec:automation-entities}), managed through its own dialog (Section~\ref{sec:frontend-academic-year-tools}). Its \texttt{matchRange} tests whether the occurrence's whole span overlaps a vacation period, and every violation carries a \texttt{messageParams.vacationLabel} naming the period matched, e.g. ``The end coincides with the vacation period `Christmas break'\thinspace''. Holiday follows the same shape, using \texttt{date-holidays}' \texttt{isHoliday} lookup as \texttt{matchDay}.

\subsection{Rule Dispatch} \label{sec:rule-dispatch}

Individual rule definitions are only half of the engine: something still has to decide, for every occurrence of every event, which rules apply and collect their results into a single report. That is \texttt{CalendarService.collectEventRuleIssues} (Appendix~\ref{app:collect-issues}, Listing~\ref{lst:collect-issues-full}), the actual entry point of the engine that both \texttt{validateAcademicYear} and \texttt{migrateAcademicYear} (Section~\ref{sec:migration-engine}) call to produce their issue reports.

A single \texttt{context} object (\texttt{allEvents}/\texttt{academicYearStart}/\texttt{vacations}) is built once per event and shared across every rule invocation for it, so cross-event rules never fetch their own data. Occurrences are sorted chronologically first, and a small shared closure flattens every violation into a self-contained issue, so both the always-on built-in rules and every explicitly attached rule share the same construction logic instead of repeating it. Because \texttt{validateAcademicYear} and \texttt{migrateAcademicYear} both call this exact method, the read-only ``Validate'' check and the automatic check after a migration can never disagree about what counts as a violation.

\section{Notifications} \label{sec:backend-notifications}

Beyond validating dates against institutional rules, EduCal reminds users of occurrences coming up soon, through an in-app notification system rather than the email-based templates originally scoped under RF04 (Section~\ref{sec:functional-requirements}); the remaining, undelivered part of that requirement is discussed in Chapter~\ref{cap:future-work}. Each event carries a default lead time, \texttt{notifyDaysBefore}, and any occurrence may override it with \texttt{notifyDaysBeforeOverride}, both set in the event/occurrence form (Section~\ref{sec:frontend-event-dialogs}). \texttt{ensureGenerated} runs lazily, on every read, comparing the current date against each occurrence's effective lead time in working days (Section~\ref{sec:backend-service}), rather than on a schedule. A notification, once generated, is a single row shared by every user, keyed uniquely by \texttt{occurrenceId}; read status is tracked separately, per user, in \texttt{notification\_reads} (Section~\ref{sec:data-model}), so marking one read for one user never affects whether another still sees it as unread. If an occurrence's date or lead time changes after generation, the stale record is deleted and regenerated, and notifications for deleted occurrences are cleaned up the same way.

\section{Tests} \label{sec:backend-tests}

An automated test suite, built with Vitest~\cite{vitest}, covers the system's pure-logic layer: the business rules and the rule dispatcher (Section~\ref{sec:rule-engine}), the working-day calculation utility, password hashing/verification, the \texttt{withRolePolicy} wrapper (Sections~\ref{sec:backend-authentication},~\ref{sec:backend-rbac}), the academic-year date helpers (Section~\ref{sec:migration-engine}), and the notification service's lead-time logic (Section~\ref{sec:backend-notifications}, exercised against an in-memory fake of its repository). It comprises 13 test files and 79 tests, all passing, reaching approximately 98\% statement coverage on the files it targets (\texttt{@vitest/coverage-v8}); the test process's timezone is pinned to UTC and cases use fixed calendar dates, including real Portuguese holidays, so results never depend on the host's timezone or the current date.

The service layer, the data-access layer (PostgreSQL and Redis), API routes, and the frontend are covered by manual testing instead: exercising each requirement's flows through the UI and, for API endpoints, direct HTTP requests. The application was also tried by a small group of ISEL academic staff on their own initiative, with generally positive feedback leading to several UI adjustments.
